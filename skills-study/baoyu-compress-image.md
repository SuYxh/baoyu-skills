# baoyu-compress-image Skill 深度解读

## 一、基础信息速览

| 维度 | 内容 |
|------|------|
| **名称/版本** | `baoyu-compress-image` v1.56.1 |
| **一句话定位** | 图片压缩工具——自动选择最佳可用工具将图片压缩或转换格式 |
| **触发关键词** | compress image、optimize image、convert to webp、reduce image file size |
| **前置依赖** | `bun` 或 `npx`（运行 main.ts）；压缩工具自动检测，无需预装 |
| **适用场景** | 单张图片压缩、目录批量处理、格式转换（PNG→WebP）、为其他 skill 提供图片瘦身 |
| **输入→输出** | 图片文件/目录 → 压缩后的 webp/png/jpeg 文件 + 压缩率报告 |

## 二、架构与设计模式分析

### 2.1 极简 Workflow——零摩擦设计

与 `baoyu-comic` 的九步流水线形成鲜明对比，本 skill 的 workflow 只有一步：**接收输入 → 执行压缩 → 报告结果**。没有 Confirmation Policy（不需要用户确认参数），没有首次设置阻塞（EXTEND.md 纯可选），没有中间产物审阅门。

这种"零摩擦"设计的核心假设是：**压缩操作是低风险、高确定性的**。用户说"压缩这张图"时，期望立即得到结果，而非被追问"你确定要 WebP 格式吗？"。

### 2.2 工具选择链——自动降级策略

```
WebP 格式:  cwebp → ImageMagick → Sharp (npm)
PNG/JPEG:   sips (macOS) → ImageMagick → Sharp (npm)
```

`detectCompressor()` 函数实现了一条**逐级探测、自动降级**的工具链。设计精髓在于：

1. **优先系统原生**：macOS 上 `sips` 零安装即可用；
2. **次选专用工具**：`cwebp` 是 WebP 格式的官方编码器，质量最佳；
3. **兜底 npm 包**：Sharp 通过 `bun`/`npx` 动态引入，确保任何环境都能运行。

这意味着 skill 在裸机 macOS 上开箱即用，在 Linux CI 环境同样不会报错——**永远有一条路径能走通**。

### 2.3 单脚本架构

整个实现浓缩在一个 ~317 行的 `main.ts` 中，职责分层清晰：
- 参数解析层（`parseArgs`）
- 工具检测层（`detectCompressor` + `commandExists`）
- 压缩执行层（四个 `compressWithXxx` 函数）
- 文件管理层（`processFile` + `collectFiles`）
- 输出层（人类友好文本 / JSON 两种模式）

没有拆分多文件、没有引入框架——**单文件即整个 skill 的全部逻辑**。

### 2.4 EXTEND.md——可选而非必需

配置查找遵循三级优先级（项目 > XDG > 用户 Home），但 **"If none found, use defaults"** 是关键原则。skill 本身硬编码了合理默认值（format: webp, quality: 80），让零配置用户也能获得良好体验。

## 三、核心能力拆解

### 3 种输出格式

| 格式 | 适用场景 | 默认质量 |
|------|---------|---------|
| **webp** | Web 发布、体积最优（默认） | 80 |
| **png** | 需要无损透明通道 | 80 |
| **jpeg** | 照片类、兼容性优先 | 80 |

### 单文件 vs 目录递归

- 输入为文件：直接处理，支持 `--output` 自定义输出路径
- 输入为目录：遍历收集 `.png/.jpg/.jpeg/.webp/.gif/.tiff`，逐一处理
- `--recursive` 开启后递归子目录

### --keep 保留原文件

默认行为是**替换原文件**（原文件重命名为 `_original` 后缀作为安全网）。`--keep` 让原文件完全不动，新文件改用 `-compressed` 后缀。

### JSON 输出模式

`--json` 输出结构化 JSON，包含每个文件的 inputSize/outputSize/ratio/compressor 字段。这使得本 skill 可以被其他脚本 pipeline 式调用——这是"工具型" skill 的标志性设计。

## 四、Prompt Engineering 学习点

### 4.1 "最小可用 skill" 的设计模板

本 skill 是一份教科书级的模板：

- **SKILL.md 只有 80 行**：一个表格说清选项，几个示例覆盖全部用法
- **无 Image Generation Tools 声明**：因为不需要 AI 生成图片
- **无 Confirmation Policy**：因为操作可逆、结果确定
- **无多步 workflow**：因为输入输出关系是 1:1 映射

### 4.2 "减法设计"的价值

复杂 skill（如 `baoyu-comic`）需要确认步骤是因为：生成成本高、结果不可预测、用户偏好多样。而压缩图片**没有这些问题**——移除所有"重型机制"不是偷懒，而是对问题域的精准理解。

### 4.3 工具链降级策略的设计价值

这个模式值得复用到任何需要调用外部工具的 skill：
1. 探测可用性（`which` 命令）
2. 按"质量/效率"排序优先级
3. 确保有一个**纯 npm 兜底方案**

这样 skill 不会因为用户未安装某个工具而失败，降低了 onboarding 阻力。

### 4.4 作为其他 skill 的"隐性依赖"

在 `baoyu-comic` 中，角色表需要压缩后才能作为 `--ref` 传递给图片生成 API（避免 payload 过大）。虽然 comic skill 内联了 `sips` 命令，但 `baoyu-compress-image` 提供了一条**标准化、跨平台的压缩路径**，可以被任何需要图片瘦身的 skill 调用。

这揭示了一个设计原则：**工具型 skill 的真正价值不只是面向用户，更是作为 skill 生态的基础设施层**。

## 五、教学小结

### 3 条 Takeaway

1. **不是所有 skill 都需要确认流程**——当操作低风险、结果确定时，零摩擦 > 安全感仪式
2. **降级策略是鲁棒性的核心**——永远给自己留一条路径能跑通，用户不应为环境差异买单
3. **单文件 + 合理默认值 = 最强可维护性**——代码越少，bug 越少，理解成本越低

### "工具型" Skill 的设计原则

| 原则 | 体现 |
|------|------|
| 即用即走 | 无状态、无需初始化、无需确认 |
| 输入输出明确 | 文件进 → 文件出，支持 JSON 供管道消费 |
| 环境自适应 | 自动检测可用工具，不强制安装 |
| 可组合 | 能被其他 skill 作为子步骤调用 |

### 复杂 vs 简单 Skill 的设计边界

| 需要复杂流程的信号 | 适合极简设计的信号 |
|-------------------|-------------------|
| 生成成本高（API 调用、长时间运算） | 操作快速、可重试 |
| 结果不可预测（AI 生成内容） | 输入决定输出（确定性转换） |
| 用户偏好空间大（风格/布局/色调） | 参数少且有合理默认值 |
| 中间产物有审阅价值 | 无中间状态 |

**核心判断标准**：如果用户说"帮我做 X"后，你需要反问 3 个以上问题才能开始——那需要确认流程。如果一个默认值就能让 80% 用户满意——极简即正义。
